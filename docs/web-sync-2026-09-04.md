## Scope and behavior

Existing API v1 RATE_LIMITED/429 and SERVICE_UNAVAILABLE/503 envelopes preserve the customer-safe message and support reference. Existing older Android versions can decode these envelopes; no forced upgrade is needed for server enforcement.

Interview video uses the existing protected-upload message formatter so processing pauses remain visible. Nia companion behavior and saved-content access are unchanged.

A 429 without Retry-After stops background upload retries while retaining encrypted originals; manual “Retry protected uploads” remains available. This conservative behavior also applies to transient 429 responses without a retry timer. Timed 429 responses and 503 retain existing retry behavior. Local media is removed only on an explicit server acknowledgement of durable storage and verified integrity. No new server codes, endpoints, permissions or persistent resources are introduced.

## Security synchronization — archive export, provider URLs and native admission

Assessed against customer-app commit `846fc9b`:

- Multipart archive export is web-only. Android opens the fixed HTTPS Account route in the system browser and intentionally never generates, receives, caches, saves or shares an export file. The web page owns the secure plan and bounded part downloads, so Android does not parse part URLs or attach a native bearer token to them.
- Android has no Google Photos connection, picker-session, persisted provider URL or Google Photos access-token path. Its media reader accepts only HTTPS signed-storage URLs without HTTP user-info on a `*.supabase.co` host, port 443, and the exact `/storage/v1/object/sign/` path; it attaches no Authorization header. A new regression covers Google media URLs, misleading host suffixes, URL credentials, cleartext, alternate ports and unrelated paths and proves they are rejected before a network request.

The shared service owns the active 15-argument `admit_mobile_identity` invocation and passes `p_handoff_hash: null` for this flow. Android neither names nor selects the removed 14-argument overload.

No runtime Android parity change is required. These server changes are backward compatible with currently shipped Android clients. The security regression and this recorded impact assessment are the only native changes. ### Corrected media AI opt-in contract

This finding supersedes the initial 7 September assessment that no Android runtime change was required: that assessment verified processing consent checks but missed the versioned Settings opt-in contract.

Settings now decodes the server's purpose-specific `consentCopy` and `consentVersions` maps with empty defaults for older responses. Each photo/video section shows the full server-authored disclosure, its current effective On/Off status, an explicit Allow action when off, and a separate Turn off/Keep off action. Opt-in is disabled when the disclosure or version is absent or blank. No consent version or processor disclosure is invented or hardcoded in native runtime code.

Before enabling, the repository reloads server preferences and compares both the version and full text to the disclosure the customer reviewed. A missing, changed or unavailable disclosure prevents the PATCH. The PATCH includes only the enabled purpose's reviewed `consentVersions` entry. The server independently checks the current version, so a change between re-read and PATCH is still rejected. Errors are displayed without optimistic success and the screen reloads current disclosures for another explicit decision. Withdrawal sends false without requiring disclosure metadata or a preflight read. Both purposes can be kept off independently. The shared authenticated client continues to send `X-Narratrace-Platform: android`.

Five additional behavioral/contract regressions cover exact server copy/version decoding, purpose-bound wire payloads, missing/blank/mismatched disclosures, fresh opt-in, stale version or text and failed reload with zero mutations, and disclosure-independent withdrawal with surfaced server failure. The previous versionless Settings mutation path was replaced rather than retained. The shared helper is exercised by the repository and uses the same request-body validation as the API.

Accessibility implementation uses normal scalable text, separate semantic headings, full-width Material buttons with explicit action labels, and a polite live region for resulting status messages. The disclosure is inline within the existing scrolling Settings layout, so it is not restricted to a modal or fixed-height text area. Device TalkBack/large-font validation remains explicitly pending because no device is attached.
